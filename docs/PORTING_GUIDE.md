# Porting Guide

## Principle

Port behavior from the official C# compiler first. Make Rust idiomatic only
where it does not change semantics or obscure the one-to-one mapping needed for
review.

## Standard Porting Loop

1. Pick one unchecked task from `PLAN.md`.
2. Read the relevant C# parser and parsed hierarchy files.
3. Identify the runtime objects or JSON shape generated by that C# code.
4. Read the matching Rust runtime implementation in `blade-ink-rs/lib/src`.
5. Implement the smallest Rust slice.
6. Add tests for the slice.
7. Run validation.
8. Update `PLAN.md` and `DOCUMENTATION.md`.

## Naming

- Preserve public concept names: `Compiler`, `InkParser`, `StringParser`,
  `Story`, `Object`, `FlowBase`, `Weave`, `Choice`, `Divert`, `Gather`.
- Use Rust module names: `snake_case` modules and `CamelCase` types.
- Prefer C# field names translated to Rust conventions when the meaning is
  identical.
- Avoid inventing replacement terminology.

## Handling C# Inheritance

The C# parsed hierarchy depends on inheritance and virtual methods:

- `runtimeObject`
- `GenerateRuntimeObject`
- `ResolveReferences`
- `FindAll`
- parent traversal

Rust options:

- Traits for shared behavior.
- Enums for closed sets of node variants.
- `Rc<RefCell<_>>` only where parent/child mutation makes it necessary.
- Stable IDs or arenas if parent traversal becomes too complex.

Choose the simplest option that can preserve C# behavior and remain testable.
Record non-obvious decisions in `DOCUMENTATION.md`.

## Runtime Integration

Before implementing a compiler export feature:

- Find the C# runtime type being generated.
- Find the Rust runtime type or JSON reader behavior in `blade-ink-rs`.
- Prefer generating JSON that the Rust runtime already accepts.
- Avoid modifying `blade-ink-rs` unless no compiler-side adapter can work.

## Diagnostics Compatibility

The official compiler often continues collecting multiple errors and warnings.
Do not collapse everything into first-error-only behavior if the C# compiler
collects richer diagnostics for that feature.

## Test Expectations

Each ported feature should include at least one of:

- Parser unit test.
- Parsed hierarchy unit test.
- JSON export golden test.
- Runtime smoke test through `bladeink`.
- Diagnostic test for an invalid input.
